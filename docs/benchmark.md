# 性能基准：10 万条工单深分页优化

2026-11-23 测量 REST 查询和工单状态操作。以分页优化前后的相同规模数据比较，可用下文的运行器和配置复测。

## 复现

在仓库根目录使用现有 Maven 缓存打包，再将 MySQL 8.4 的 `bin` 目录和 JDK 25 的 `java.exe` 路径传给脚本。每个规模使用全新的回环实例和合成账号，依次运行。脚本把结果 JSON 写到标准输出，进度写到标准错误，并核对自建进程退出、监听端口释放、自建目录清理。失败时保留经过筛选的错误信号。

```powershell
$mysqlBin = 'C:\path\to\mysql\bin'
$javaExe = (Get-Command java.exe -ErrorAction Stop).Source
.\mvnw.cmd --offline --batch-mode '-Dmaven.test.skip=true' package
node scripts/benchmark/run-local.mjs $mysqlBin $javaExe target/fixcampus-0.0.1-SNAPSHOT.jar 10000
node scripts/benchmark/run-local.mjs $mysqlBin $javaExe target/fixcampus-0.0.1-SNAPSHOT.jar 100000
node scripts/benchmark/run-local.mjs $mysqlBin $javaExe target/fixcampus-0.0.1-SNAPSHOT.jar 100000 study
node scripts/benchmark/run-local.mjs $mysqlBin $javaExe target/fixcampus-0.0.1-SNAPSHOT.jar 100000 pagination
```

以上命令用于各自的历史测量版本。复测原基线时使用优化前的 JAR，分页优化复测用优化后的历史 JAR 加 `pagination`。`study` 的 50 秒与 1 秒锁等待对照也使用对应历史 JAR。当前 Web Profile 固定以 3 秒初始化数据库连接，锁等待验收应参考当前版的真实 MySQL 集成用例。

## 测量条件

- Windows，Intel Core i5-12490F，12 逻辑核，16,197 MiB 系统内存。Node 24.19.0、JDK 25.0.4.1、Spring Boot 3.5.16、MySQL 8.4.11。
- JVM 最大堆 512 MiB，Hikari 最大连接数 3，连接借用超时 5 秒。MySQL InnoDB 缓冲池 128 MiB，最大连接数 151，基线会话行锁超时 50 秒。基线关闭缓冲池转储／恢复和 MySQL binlog。测量客户端、应用和数据库在同机运行。
- 10,000／100,000 工单，24,500／245,000 个配套事件，50 名学生，12 名维修人员。主学生持有 25% 工单，主维修人员持有约 30% 已分配工单。状态按待分配 35%、待维修 20%、维修中 15%、待确认 10%、已完成 15%、已撤销 5% 分布。时间按固定间隔跨约 11／112 天。低选择性关键词约匹配 10%，高选择性关键词约匹配 1%。
- 读取每类先记录一次接口响应，随后预热 8 次，再用 4 个并发请求槽测 120 个样本。延迟从客户端发请求计到响应正文收完，包含同机网络和应用开销。首个接口样本前已完成造数、统计信息收集和 SQL 校验，本轮的首个样本来自已启动的应用和已访问的数据页。磁盘冷启动和跨机负载尚未测量。
- 用实际接口结果核对 SQL 推导出的总数、排序和页内工单编号。详情核对工单及事件。Hikari 连接、线程等待、JVM 堆和进程 CPU 通过本机 JMX 按约 50 ms 采样。

## 基线结果

每格为吞吐（请求/秒）／P95／P99（毫秒）。各读场景两档各 120 个计量样本，HTTP 错误率均为 0%。两档读场景计量累计 2.29／7.08 秒，各场景时长、首个请求和资源采样记录于原始 JSON。

| REST 场景 | 10,000 条 | 100,000 条 |
| --- | ---: | ---: |
| 管理员列表首页 | 460.10 / 12.34 / 24.84 | 207.63 / 27.05 / 35.03 |
| 管理员按状态筛选 | 510.30 / 13.68 / 34.62 | 258.08 / 21.30 / 26.23 |
| 管理员常见关键词 | 415.49 / 13.26 / 22.67 | 108.74 / 50.52 / 58.31 |
| 管理员稀有关键词 | 337.59 / 15.80 / 18.60 | 113.62 / 45.55 / 51.16 |
| 管理员末页 | 253.98 / 20.52 / 26.45 | 46.41 / 123.02 / 133.08 |
| 学生列表首页 | 441.06 / 14.28 / 16.62 | 138.42 / 42.83 / 46.96 |
| 维修人员列表首页 | 694.66 / 20.67 / 29.70 | 657.73 / 8.18 / 14.86 |
| 管理员工单详情 | 516.81 / 10.30 / 11.74 | 497.48 / 12.96 / 29.31 |

MySQL 的实际执行计划显示，10 万条下管理员末页扫描并排序 100,000 行，返回 20 行，单次计划根节点约 55.8 ms。无条件 `COUNT(*)` 约 7.15 ms。稀有关键词页数据通过 `idx_orders_created` 扫描 1,930 行后返回 20 行，同一条件的 `COUNT(*)` 扫描 100,000 行，约 30.8 ms。学生和维修人员首页分别使用 `idx_orders_student_created` 和 `idx_orders_worker_created`，各读出 20 行。MySQL statement digest 记录了实际 SQL 归一化形状、执行次数和累计扫描行数。

| 写入场景 | 每档样本 | 10,000 条 P95 | 100,000 条 P95 | 每档 HTTP 结果 |
| --- | ---: | ---: | ---: | --- |
| 六并发派单给不同工单 | 24 | 54.04 ms | 55.22 ms | 24 次 204 |
| 同一工单双派单 | 24 | 23.50 ms | 26.18 ms | 12 次 204，12 次预期 409 |
| 同一工单撤销与派单竞争 | 24 | 20.61 ms | 23.45 ms | 12 次 204，12 次预期 409 |
| 持有目标行锁约 2 秒后释放 | 6 | 2015.57 ms | 2011.70 ms | 1 次 204，5 次预期 409 |

逐单核对竞态结束时的状态和事件，观测到一次状态转换，两档意外 HTTP 错误均为 0。持锁时 MySQL `data_lock_waits` 观测到 6 条等待关系，Hikari 同时观测到 3 个活动连接和最多 3 个等待连接的线程。10 万条用例中的 JVM 峰值采样为 107.3 MiB。

## 10 万条对照

在同一数据集上，交替执行原管理员末页 SQL 和先取页内 ID、再按主键取详情的候选 SQL。各预热 1 次并计量 6 次 `EXPLAIN ANALYZE`。计划根节点中位耗时从 54.8 ms 降到 13.7 ms。候选查询通过 `idx_orders_created` 扫描 100,000 个索引项，并按主键回表 20 次。升序和降序分别在偏移量 0、20、50,000、99,980 逐列比对，返回结果一致。

对同一实例施加约 2.5 秒的目标行锁，并从 MySQL `performance_schema.variables_by_thread` 核对应用连接的实际设置。原本的 50 秒超时下，派单等到释放后在 2521.94 ms 返回 204，写入一条派单事件。将隔离实例的新连接超时设为 1 秒、通过本地 JMX 换掉连接池旧连接后，同类请求在 1042.74 ms 返回 503，工单仍待分配且只有原提交事件。当前 JPA 锁查询使用 `PESSIMISTIC_WRITE`，未声明查询级超时提示。两次测量均实见 MySQL 行锁等待。该对照只运行一次，结论限于超时行为和状态一致性。

## 接入 REST 后复测

管理员无筛选列表从第二页起先从排序索引取页内 ID，再按主键加载该页。第一页、带筛选的查询和维修人员列表走原查询。COUNT、页码、总页数和 `created_at, id` 排序沿用原契约。

复用 10 万条数据生成规则、资源配置、读取场景顺序和 4 个并发请求槽。每个场景 120 个计量样本，HTTP 错误率均为 0%。

| 场景 | P95 基线 → 复测 | P99 基线 → 复测 | 吞吐基线 → 复测 |
| --- | ---: | ---: | ---: |
| 管理员末页 | 123.02 → 39.88 ms | 133.08 → 46.18 ms | 46.41 → 137.45 请求/秒 |
| 管理员首页 | 27.05 → 26.51 ms | 35.03 → 28.23 ms | 207.63 → 220.22 请求/秒 |

MySQL 记录该 REST 查询执行 129 次，对应首个样本、8 次预热和 120 次计量。实测同形查询使用 `idx_orders_created`，执行计划根节点耗时 13.6 ms，并按主键读取 20 行。HTTP 检查覆盖总数、总页数、页内编号、同时间戳的双向排序、越界空页、筛选第二页，以及维修人员请求管理员分页时返回 403。

这是两个本机测量窗口的结果。维修人员首页的查询路径相同，单轮 P99 从 14.86 ms 到 24.84 ms。各场景原始结果保留在私人证据中。
